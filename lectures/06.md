# Лекция 6. Инструменты и среда агента

## Введение. Рабочая среда сотрудника

Агентный цикл связывает решение языковой модели с наблюдением и действием во внешней среде. После организации контекста и распределения работы между агентами возникает вопрос об интерфейсах: как система получает данные, выполняет операции и получает сведения о результате? В этой лекции рассматриваются контракт инструмента, его подключение, среда исполнения и доступ к корпоративным сервисам.

Сквозной учебный запрос сотрудника: «Разбери жалобу клиента после релиза, собери переписку и документацию, проверь метрики, найди связанные изменения и подготовь задачу разработчикам и ответ поддержке». Агенту нужны рабочие обсуждения, документы, аналитическая база и система задач. Исследование причины может потребовать самостоятельного исполнителя. Значения INC-42, r41/r42, номера проектов, адреса example и ответы инструментов в примерах вымышлены.

Angie Jones описывает корпоративное применение Goose в Block в апреле 2025 года. Подготовленные MCP-интеграции дали сотрудникам агентный интерфейс к рабочим системам. Публикация служит примером мотивации общей рабочей среды; наш инцидент не является production-трассой Block. [MCP in the Enterprise: Block](https://dev.to/goose_oss/mcp-in-the-enterprise-real-world-adoption-at-block-ci5).

**Harness** здесь обозначает исполняющее агентное приложение: оно управляет диалогом, контекстом и вызовами зарегистрированных операций. Сначала рассмотрим простую функцию внутри приложения, затем независимую интеграцию и её исполнение. Предметные определения вводятся перед соответствующим механизмом.

Редакция материалов от 9 ноября 2026 года содержит 74 карточки. Полный подробный разбор рассчитан ориентировочно на 120–130 минут. Вариант на 90 минут предполагает более краткое чтение технических сообщений, но сохраняет объяснение терминов и все карточки. Подробности темпа приведены в [дизайне](design.md); соответствие старых и новых номеров — в [карте редакции](revision-map.md).

## Глава I. Где исполняется инструмент

### I.1. Локальная функция

Модель выбирает имя инструмента и аргументы. Harness разбирает этот вызов и передаёт его зарегистрированной функции. Функция обращается к сервису, а её результат становится наблюдением следующего шага агентного цикла.

Pydantic AI строит схему входа по параметрам функции, исключая `RunContext`. Поэтому `incident_id` выбирает модель, а объект `IncidentStore` приложение создаёт и передаёт через `deps`. Dependencies — обычные зависимости приложения: клиенты сервисов, соединения с базами и настройки. Объект клиента не попадает в контекст модели автоматически. [Pydantic AI: Tools](https://pydantic.dev/docs/ai/tools-toolsets/tools/), [Dependencies](https://pydantic.dev/docs/ai/core-concepts/dependencies/).

В этой лекции **built-in инструмент** — функция, зарегистрированная и вызываемая внутри агентного приложения. Это удобный вариант для прямого вызова, общей отладки и использования зависимостей приложения. Если интеграцию надо подключать к другим приложениям, возникают вопросы упаковки, версий и адаптации. Возможна общая библиотека. MCP предлагает другой способ: независимого поставщика с согласованным протоколом подключения.

В типизированном локальном инструменте функция использует переданный приложением клиент хранилища:

```python
@agent.tool
async def read_incident(
    ctx: RunContext[IncidentStore], incident_id: str
) -> dict:
    """Прочитать доступный сотруднику инцидент.

    Args:
        incident_id: Идентификатор, например INC-42.
    """
    return await ctx.deps.read_visible(incident_id)
```

Фрагмент предполагает `Agent(deps_type=IncidentStore)` и передачу зависимости через `deps` при запуске. Полный [автономный пример](examples/local_tool.py) использует `FunctionModel`: без сети выполняет настоящий tool call и проверяет возвращённый результат. Дополнительная проверка доступа в примере относится к главе III. `async`-функция работает в асинхронном контексте; синхронную функцию Pydantic AI может выполнять в thread pool. Отдельный поток не означает отдельный процесс. [Pydantic AI: Tools](https://pydantic.dev/docs/ai/tools-toolsets/tools/), [Pydantic AI: Dependencies](https://pydantic.dev/docs/ai/core-concepts/dependencies/).

### I.2. MCP: роли, сообщения и размещение

MCP расшифровывается как Model Context Protocol. **Host** — агентное приложение, которое координирует модель, контекст и цикл. **Client** — его протокольный компонент для взаимодействия с одним сервером. **Server** — поставщик инструментов, который реализует операции через свой код и существующие API. Host может создавать несколько clients. [MCP: Architecture, редакция 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/architecture).

JSON — текстовый формат структурированных данных. RPC (Remote Procedure Call) — вызов процедуры через сообщения. **JSON-RPC 2.0** задаёт конверт: `method` указывает процедуру, `params` содержит вход, а `id` связывает запрос с ответом. Ответ содержит `result` либо `error`. На слайде `subtract` служит отдельным учебным примером JSON-RPC, не MCP запросом. [JSON-RPC 2.0](https://www.jsonrpc.org/specification).

#### Каталог tools и контекст модели

Предположим, в host настроен адрес `https://incidents.example/mcp`. Client может запросить `server/discover`, чтобы узнать поддерживаемые версии и capabilities. В нашем примере ответ сообщает `2026-07-28` и поддержку `tools`. Для client discovery опционален, поэтому его нельзя понимать как обязательный handshake. Следующий `tools/list` возвращает `read_incident`, `search_incidents`, `create_incident`. [MCP: Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover).

Host выбирает для текущей задачи определение `read_incident` и передаёт его модели. Этот выбор контекста — политика приложения, отдельная от протокольного обнаружения возможностей сервера. Пример определения:

```json
{
  "name": "read_incident",
  "description": "Прочитать инцидент по идентификатору",
  "inputSchema": {
    "type": "object",
    "properties": {"incident_id": {"type": "string"}},
    "required": ["incident_id"]
  }
}
```

Модель выбирает `read_incident` с `INC-42`. После допуска вызова host его client формирует `tools/call`. В редакции 2026-07-28 каждый запрос несёт `_meta` с версией протокола и capabilities. `clientInfo` рекомендован, но не обязателен. Использовать старый `initialize` в основной последовательности этой редакции не требуется. [MCP: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [Base protocol: per-request metadata](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#_meta).

#### stdio и Streamable HTTP

**stdio** связывает локальные процессы через стандартные потоки. Client запускает server как отдельный дочерний процесс. Запрос идёт в `stdin` сервера, ответ — из `stdout`. Каждое сообщение занимает одну строку JSON-RPC, а логи можно писать в `stderr`. [MCP: stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio).

**HTTP** — прикладной протокол запросов и ответов. Streamable HTTP отправляет каждый JSON-RPC запрос отдельным POST на один endpoint. В учебном deployment server расположен на другой машине. HTTP возможен и локально. Ни размещение процесса, ни выбранный транспорт сами по себе не задают ограничения ресурсов.

Заголовок `Content-Type` указывает формат тела. `Accept` сообщает допустимые форматы ответа. **SSE (Server-Sent Events)** — текстовый поток событий в HTTP ответе с `Content-Type: text/event-stream`. Поле `data` содержит данные события, пустая строка его завершает. Это один из вариантов ответа в Streamable HTTP. Server может вернуть обычный JSON объект. [WHATWG: Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html).

#### Два формата ответа и границы события

Учебный `tools/list` с `id=7` может получить один JSON объект либо тот же объект внутри SSE. Это альтернативные ответы на один запрос, а не два последовательных ответа. В HTTP примерах ответа ниже показаны status и `Content-Type`, остальные заголовки и framing HTTP тела опущены. Полные учебные запросы используют вымышленный `tools.example`; каждое однострочное UTF-8 тело передаётся без завершающего перевода строки, что учтено в `Content-Length`.

```http
POST /mcp HTTP/1.1
Host: tools.example
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/list
Content-Length: 170

{"jsonrpc":"2.0","id":7,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}
```

Обычный JSON ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"jsonrpc":"2.0","id":7,"result":{"resultType":"complete","tools":[]}}
```

Тот же ответ как одно SSE событие:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"jsonrpc":"2.0","id":7,"result":{"resultType":"complete","tools":[]}}

```

Физическая пустая строка после `data` завершает событие. `event: message` необязателен: при отсутствии `event` используется тип `message`. Это имя события SSE и JSON-RPC `method` внутри JSON — разные уровни. На слайдах символ **↪** помечает только экранное продолжение длинной строки. Он не передаётся по сети и не создаёт LF. Серое поле «пустая строка» обозначает реальный разделитель. Во всех полных примерах конспекта каждая строка `data:` содержит один полный JSON объект. [WHATWG: формат SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation).

Далее приведены **три независимых HTTP ответа** на три разных запроса. На слайдах каждый ответ занимает две соседние карточки: вторая продолжает тело первого, не открывая новый HTTP ответ. `method` без JSON-RPC `id` обозначает уведомление; итоговый response с `id` соотносится с исходным запросом. В каждом запросе `params._meta` содержит обязательные поля `io.modelcontextprotocol/protocolVersion` и `io.modelcontextprotocol/clientCapabilities`. Пустой объект client capabilities достаточен для этих примеров. Заголовки `MCP-Protocol-Version`, `Mcp-Method` и, для `tools/call`, `Mcp-Name` согласованы с телом. [MCP: метаданные и HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#request-metadata).

#### Пример 1. Ход выполнения долгого tools/call

Client выбирает отдельный `progressToken="job-1"` в `params._meta` запроса с JSON-RPC `id=1`. Имя `process_files` и результаты учебные. Токен должен быть уникален среди активных запросов. Server может отправлять уведомления о ходе, но не обязан их отправлять. [MCP: Progress](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/progress).

```http
POST /mcp HTTP/1.1
Host: tools.example
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: process_files
Content-Length: 232

{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{},"progressToken":"job-1"},"name":"process_files","arguments":{}}}
```

Первый независимый HTTP ответ, полное тело SSE из трёх событий:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"job-1","progress":10,"total":100,"message":"Обработано 10 файлов"}}

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"job-1","progress":70,"total":100,"message":"Обработано 70 файлов"}}

data: {"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","content":[{"type":"text","text":"Готово. Обработано 100 файлов, ошибок нет."}]}}

```

Между двумя уведомлениями могут пройти секунды или минуты. `progress` возрастает с 10 до 70, `total=100` задаёт ожидаемый объём. У `notifications/progress` нет `id`: `progressToken` связывает сведения о ходе с выполняемой операцией. Итог имеет `id=1` и `resultType="complete"`; `result.content` содержит результат инструмента. Физическая пустая строка после каждого уведомления завершает событие, HTTP ответ продолжает передаваться. В показанном случае server закрывает поток после финального response, как рекомендует норма **SHOULD terminate**. Это не правило закрывать соединение после каждого progress. [MCP: Receiving Messages](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#receiving-messages).

#### Пример 2. Сообщения logging перед результатом

**Logging deprecated с MCP 2026-07-28**, но пока остаётся в спецификации. Пример нужен для чтения существующего протокольного обмена. Новым реализациям спецификация рекомендует не внедрять эту возможность; для stdio предлагается `stderr`, для структурированной наблюдаемости — OpenTelemetry. Server, отправляющий `notifications/message`, обязан объявить capability `logging`. Ниже именно фрагмент результата `server/discover`, не полный запрос или ответ:

```json
{"capabilities":{"logging":{}}}
```

Client включает `io.modelcontextprotocol/logLevel="info"` в `params._meta` конкретного `tools/call id=2`. Допустимы сообщения уровня info и выше, в том числе warning. Без этого поля server не должен присылать `notifications/message` для запроса. Эти сообщения идут в ответе именно этого вызова, а не в потоке подписки. [MCP: Logging, редакция 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/logging).

```http
POST /mcp HTTP/1.1
Host: tools.example
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: build_report
Content-Length: 249

{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{},"io.modelcontextprotocol/logLevel":"info"},"name":"build_report","arguments":{}}}
```

Второй независимый HTTP ответ, полное тело SSE из трёх событий:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"jsonrpc":"2.0","method":"notifications/message","params":{"level":"info","logger":"report","data":{"message":"Начинаю сбор данных"}}}

data: {"jsonrpc":"2.0","method":"notifications/message","params":{"level":"warning","logger":"report","data":{"message":"Один источник недоступен, использую кэш"}}}

data: {"jsonrpc":"2.0","id":2,"result":{"resultType":"complete","content":[{"type":"text","text":"Отчёт готов. Для одного источника использованы данные из кэша."}]}}

```

В уведомлениях `params.data.message` хранит сообщение журнала, `logger="report"` обозначает источник записи. Оно не склеивается с итоговым `result.content`. После двух уведомлений без `id` приходит response `id=2` с текстом отчёта. В этом примере server завершает поток после результата, а не после info или warning. Поле `data` на уровне SSE содержит JSON целиком; вложенное `params.data` относится к схеме logging.

#### Пример 3. Длительная подписка на изменения

**Resource** в MCP — данные, предоставляемые server; **URI** — идентификатор этих данных, например `file:///config.json`. **Подписка** — запрос будущих уведомлений о выбранных изменениях. Здесь вводится только смысл, необходимый для чтения SSE; полное обсуждение Resources и Prompts остаётся в завершающей главе.

Client отправляет `subscriptions/listen id=3`, запрашивая изменения списка tools и обновления указанного ресурса. Предполагается, что server поддерживает `tools.listChanged=true` и `resources.subscribe=true`. Ниже фрагмент его объявленных capabilities:

```json
{"capabilities":{"tools":{"listChanged":true},"resources":{"subscribe":true}}}
```

Полный учебный запрос:

```http
POST /mcp HTTP/1.1
Host: tools.example
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: subscriptions/listen
Content-Length: 270

{"jsonrpc":"2.0","id":3,"method":"subscriptions/listen","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}},"notifications":{"toolsListChanged":true,"resourceSubscriptions":["file:///config.json"]}}}
```

Третий независимый HTTP ответ. Ниже все три события наблюдаемого участка; после последней пустой строки поток остаётся открыт:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"jsonrpc":"2.0","method":"notifications/subscriptions/acknowledged","params":{"_meta":{"io.modelcontextprotocol/subscriptionId":3},"notifications":{"toolsListChanged":true,"resourceSubscriptions":["file:///config.json"]}}}

data: {"jsonrpc":"2.0","method":"notifications/resources/updated","params":{"_meta":{"io.modelcontextprotocol/subscriptionId":3},"uri":"file:///config.json"}}

data: {"jsonrpc":"2.0","method":"notifications/tools/list_changed","params":{"_meta":{"io.modelcontextprotocol/subscriptionId":3}}}

```

Первым приходит `notifications/subscriptions/acknowledged`: server подтверждает принятый фильтр. Только после этого поступают выбранные change notifications. `params._meta["io.modelcontextprotocol/subscriptionId"]=3` совпадает с `id=3` запроса listen и маркирует уведомления этой подписки. У самих уведомлений JSON-RPC `id` отсутствует. `progressToken` в подписке не используется. [MCP: Subscriptions](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions).

`notifications/resources/updated` сообщает только URI изменившегося ресурса. Новое содержимое автоматически не передаётся; его получают отдельным `resources/read`. Полное JSON-RPC тело такого отдельного запроса:

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "resources/read",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    },
    "uri": "file:///config.json"
  }
}
```

`notifications/tools/list_changed` означает изменение каталога; актуальные определения можно запросить через `tools/list`. Это длительный ответ: в показанном открытом потоке **нет final response**, и после третьего события возможны новые изменения. При штатном завершении подписки со стороны server спецификация **SHOULD** предусматривает final response с `id=3`, `resultType="complete"` и `result._meta["io.modelcontextprotocol/subscriptionId"]=3`, затем закрытие потока. Это отдельная ветвь завершения, не четвёртое событие показанного примера. [MCP: Graceful Closure](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions#graceful-closure).

В Streamable HTTP 2026-07-28 каждый запрос имеет свой POST и ответ. Закрытие SSE client означает отмену соответствующего запроса. GET stream, protocol sessions и возобновление через `Last-Event-ID` не входят в эту редакцию. Progress и logging относятся к текущему вызову, change notifications — к `subscriptions/listen`. [MCP: Streamable HTTP, редакция 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).

#### MCP и ISO/OSI

ISO/OSI — семиуровневая эталонная модель сетевого взаимодействия. MCP определяет методы и их смысл. JSON-RPC задаёт конверт вызова. HTTP переносит запросы и ответы. SSE задаёт формат событий внутри HTTP ответа. В концептуальном сопоставлении все они относятся к прикладному уровню L7. Логическая вложенность сообщений не означает разные уровни OSI. stdio — локальный IPC, то есть межпроцессный обмен, вне сетевой OSI интерпретации. [ITU-T X.200](https://www.itu.int/rec/T-REC-X.200-199407-I/en).

Built-in удобен, когда инструмент поставляется вместе с одним приложением и использует его зависимости. MCP полезен для независимой интеграции, подключаемой к разным hosts. Дополнительный процесс или сервис требует обслуживания, поэтому MCP не является обязательным следующим шагом для любой локальной функции.

### I.3. Sandbox: определения и механизмы

Исполнение программы требует решения о доступных ей ресурсах. **Workload** в этом разделе — исполняемая задача: команда и запущенные ею процессы. **Sandbox** — технически обеспеченная граница доступа этих процессов к ресурсам. **Политика** — конкретные правила разрешения и запрета. Например, при запуске тестов проекта можно разрешить запись в рабочую папку, запретить чтение личного файла и ограничить адреса сетевых соединений. Это учебная политика, а не обещание настроек по умолчанию. Граница полезна, потому что тесты и установленные зависимости исполняют код: обычные права процесса могут дать ему больше доступа, чем требуется для задачи. [Codex: Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security).

**Ядро (kernel)** — часть операционной системы, управляющая процессами, памятью и доступом к ресурсам. **Системный вызов** — запрос программы к ядру: например, открыть файл или установить соединение. Обычно программа делает его через библиотеку языка. Проверки доступа выполняет ОС на пути к ресурсу; программа получает результат либо ошибку. Само указание агенту «не читай файл» не создаёт технической границы. На учебной схеме проверки объединены в один блок, хотя в реальной ОС они распределены между механизмами. [Linux man-pages: syscalls(2)](https://man7.org/linux/man-pages/man2/syscalls.2.html).

Ограничить обычный процесс можно без отдельной гостевой ОС. **Seatbelt** — механизм macOS, применяющий профиль разрешённых операций к процессу. **bubblewrap (bwrap)** — утилита Linux для сборки sandbox; она формирует для процесса отдельное представление файлов и при настройке других ресурсов. Политику определяет вызывающая программа и её параметры, а не одно наличие bubblewrap. **seccomp** — механизм Linux, фильтрующий системные вызовы. Документация ядра отдельно подчёркивает: такой фильтр уменьшает доступную поверхность ядра, но сам не составляет полный sandbox. Во всех этих случаях используется ядро основной ОС. [Codex: Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security), [bubblewrap: Sandbox security](https://github.com/containers/bubblewrap#sandbox-security), [Linux: Seccomp filters](https://docs.kernel.org/userspace-api/seccomp_filter.html).

По документации, проверенной **8 ноября 2026 года**, локальные команды Codex на macOS ограничиваются Seatbelt, на Linux — bubblewrap и seccomp. Переход Linux на bubblewrap документация связывает с версией 0.115. Claude Code использует Seatbelt на macOS и bubblewrap на Linux; встроенный shell sandbox включается отдельно. Эти сведения относятся к указанным локальным платформам, а не ко всем облачным средам продуктов. В Codex границы локальных sandboxed commands и ограничения других поверхностей настраиваются отдельно. В Claude Code shell sandbox охватывает команду и дочерние процессы; встроенные Read/Edit/Write и MCP-серверы работают вне него. Одобрение запуска и техническая граница — разные решения. Файлы с ключами и токенами и переменные среды, уже доступные программе, не скрываются автоматически словом sandbox. [Codex: Permissions](https://learn.chatgpt.com/docs/permissions), [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing).

**Контейнер** — отдельное окружение процессов с выбранными файлами и зависимостями. **Docker** — пример системы, создающей такие окружения. **Namespaces** — механизмы ядра Linux, которые задают процессам отдельное представление ресурсов, например файлов, процессов и сети. **Cgroups** учитывают и ограничивают потребление ресурсов, включая память и процессорное время; это не проверка доступа к данным. У обычных Linux-контейнеров общее ядро с **хостом**, то есть машиной, где они запущены. Контейнер удобен для воспроизводимого запуска зависимостей, но доступ зависит от конфигурации. Подключённая внутрь папка хоста остаётся доступной в рамках заданных прав. [Docker Engine: Security](https://docs.docker.com/engine/security/).

**gVisor** меняет путь обращения приложения к ОС. Его **Sentry** — программный слой, который сам реализует системный интерфейс приложения; за эту роль его называют application kernel. Системный вызов приложения не пересылается напрямую ядру хоста. Sentry обрабатывает его и при необходимости делает собственные ограниченные обращения. Мотивация — уменьшить прямое взаимодействие чужого кода с ядром общей машины. Это отдельный архитектурный выбор, требующий проверки совместимости и производительности на конкретной программе. Сетевые правила и лимиты ресурсов задаются средствами контейнера и хоста. [gVisor: Security model](https://gvisor.dev/docs/architecture_guide/security/).

**VM**, или виртуальная машина, запускает гостевую ОС на виртуальном процессоре, памяти и устройствах. Её **гостевое ядро** отличается от ядра хоста. **MicroVM** — VM с небольшой моделью виртуального оборудования. **Firecracker** — программа запуска таких microVM, управляющая их устройствами и запуском. Она использует **KVM**, механизм виртуализации в ядре Linux, для исполнения гостевого процессора. Firecracker дополнительно ограничивают как процесс хоста; эта мера дополняет границу VM. Отдельную гостевую ОС рассматривают для заданий, которым нельзя делить одну среду. Наличие VM не определяет политику сети: Firecracker сам не фильтрует исходящий трафик, это задача оператора хоста. [Firecracker: Design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md), [Linux: KVM API](https://docs.kernel.org/virt/kvm/api.html).

Выбор начинается с вопросов к задаче. Какие файлы и сетевые адреса необходимы? Какой код исполняется и что он делит с соседними задачами? Требуется ли отдельное окружение зависимостей, сокращение прямого взаимодействия с ядром или гостевая ОС? Поддерживает ли среда необходимые операции и приемлема ли стоимость запуска? Эти вопросы не задают универсального рейтинга безопасности. В любом варианте код способен использовать доступные ему файлы, ключи, токены и сервисы. Способ вызова инструмента, размещение кода и граница его исполнения — независимые решения, которые комбинируются в одной системе.

## Глава II. Как сервис становится инструментом для агента

Адаптер связывает рабочую задачу с техническим интерфейсом сервиса. Для каждого кейса полезно различать четыре уровня: исходный продукт, затруднение агента, решение создателей адаптера и границу этого решения. Вводные примеры учебные: они объясняют интерфейс сотрудника и не выдаются за выполненные обращения к рабочим системам.

### II.1. ClickHouse: от вопроса к SQL

ClickHouse — аналитическая БД, в которой события представлены таблицами, а сводки вычисляются SQL-запросами. SQL задаёт отбор строк и вычисления. В учебном сценарии сотрудник сравнивает число ошибок по версиям релиза. Агент сначала выясняет структуру данных посредством `list_databases` и `list_tables`, затем передаёт SQL в `run_query`. Пагинация метаданных, структурированные ошибки и timeout относятся к разным сторонам взаимодействия. Попытка отмены не подтверждает остановку операции; режим чтения сам по себе не ограничивает стоимость вычисления. [Продукт](https://clickhouse.com/docs/get-started/about/intro), [контракт адаптера](https://github.com/ClickHouse/mcp-clickhouse#features), [история изменений](https://github.com/ClickHouse/mcp-clickhouse/blob/main/CHANGELOG.md).

### II.2. Notion: документ поверх блоков

Страница Notion — документ из блоков, часть которых содержит дочерние элементы. В первой реализации MCP отображение endpoint в tool сохраняло для агента JSON-иерархию и служебные чтения. Создатели hosted адаптера изменили представление на Notion-flavored Markdown и переработали операции создания и обновления страниц. Это расширенная текстовая разметка, а не обещание совместимости всех блоков с обычным Markdown. Контракт `notion-fetch` сообщает о пропущенных поддеревьях через `truncated`, `unknown_block_ids` и `unknown_block_count`; возвращённый ID позволяет запросить часть отдельно, если права дают доступ. [Инженерная статья создателей](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look), [контракт чтения](https://developers.notion.com/guides/mcp/tools-search-reference#fetch-notion-content).

### II.3. GitHub Projects: предметные ссылки и разрешение ID

Project — план работы; issue — задача репозитория; item — запись задачи в конкретном проекте; field — поле этой записи; option — вариант поля с выбором. Поэтому issue #42 и соответствующий item имеют разные идентификаторы. В учебном примере агент сначала находит Support Board и выбирает `project_number=7`. Затем `projects_write` с `method=update_project_item` принимает `item_owner`, `item_repo`, `issue_number` и `updated_field` с `name` и `value`.

Полный учебный вызов MCP 2026-07-28 содержит обязательные метаданные `params._meta`: `io.modelcontextprotocol/protocolVersion` и `io.modelcontextprotocol/clientCapabilities`. Версия и возможности объявляются на каждом запросе. Пустой объект возможностей не заявляет дополнительные функции клиента; обычный вызов ниже их не требует. [MCP: обязательные поля запроса](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#_meta).

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    },
    "name": "projects_write", "arguments": {
      "method": "update_project_item",
      "owner": "acme", "project_number": 7,
      "item_owner": "acme", "item_repo": "backend", "issue_number": 42,
      "updated_field": {"name": "Status", "value": "In Progress"}
    }}
}
```

REST обозначает HTTP-интерфейс с адресами ресурсов: GET читает ресурс, PATCH изменяет его свойства. GraphQL позволяет задавать запросы и изменения через именованные поля; org в маршруте обозначает организацию. Эти определения даны на слайде перед таблицей соответствий. [REST](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api), [GraphQL](https://docs.github.com/en/graphql/guides/introduction-to-graphql).

Внешний JSON-RPC `method=tools/call` выбирает операцию MCP, а `params.arguments.method` выбирает прикладную ветку tool. По проверенному `projects.go` разрешение предметных ссылок использует GraphQL; запись обычного проектного поля Status выполняется REST Projects API. Это не mutation `updateProjectV2ItemFieldValue` в показанной ветке. Отдельный `method=create_project_status_update` действительно вызывает GraphQL `createProjectV2StatusUpdate`, но означает отчёт о ходе проекта, а не изменение Status item. Автоопределение владельца имеет предел: `create_project` требует явный `owner_type`. [Мотивация консолидации, 28 января 2026](https://github.blog/changelog/2026-01-28-github-mcp-server-new-projects-tools-oauth-scope-filtering-and-new-features/), [исходный код](https://github.com/github/github-mcp-server/blob/main/pkg/github/projects.go), [REST Projects](https://docs.github.com/en/rest/projects/items#update-project-item-for-organization).

### II.4. Playwright MCP: состояние и адресованное действие

Автоматизация браузера программно повторяет действия пользователя в веб-интерфейсе. Playwright MCP представляет страницу как accessibility snapshot: дерево ролей, названий и ссылок элементов. Агент выбирает `target` из наблюдения в момент t, вызывает `browser_click`, после чего получает обновлённое состояние t+1. Здесь показан один snapshot как текущее наблюдение, а новое наблюдение — результат изменения страницы. Ссылки могут устаревать; snapshot также не содержит всей визуальной информации. Достижение бизнес-эффекта проверяют по состоянию созданного объекта. [Контракт создателей адаптера](https://github.com/microsoft/playwright-mcp#readme), [snapshot и target](https://github.com/microsoft/playwright.dev/blob/main/mcp/snapshots.mdx).

### II.5. Инструменты делегирования и A2A

Поручение исполнителю должно содержать вопрос, контекст, границы и ожидаемый результат. В нашем сценарии это сравнение ошибок релизов r41/r42 за 30 минут с таблицей оснований. Фиксированная выборка может оставаться обычным tool; самостоятельное исследование получает собственный агентный цикл. Здесь рассматривается интерфейс такого запуска, а паттерны оркестрации остаются в лекции 5.

Subagent — дочерний агентный запуск внутри harness. В [Pydantic AI Harness](https://pydantic.dev/docs/ai/harness/subagents/) вызов `delegate_task(agent_name, task)` возвращает результат именованного агента. Его история отделена от родительской, поэтому поручение самодостаточно. В этой реализации ресурсы приложения передаются дочернему запуску, usage по умолчанию учитывается совместно, а наследование собственных tools родителя включается отдельно. Слово fork само по себе не задаёт эти правила. Отдельная история также не изолирует общий workspace.

В A2A client представляет вызывающую сторону и отправляет запросы. В нашем примере он действует от имени главного агента. A2A server обозначает исполняющую сторону, открывающую A2A endpoint агента аналитики: публикует Agent Card, принимает поручение и обеспечивает его исполнение. Client/server — роли в конкретном обмене, а не обязательное разделение систем: одна система может принимать поручения как server и обращаться к другим как client. Agent Card — JSON-описание возможностей и интерфейсов, передаваемое клиенту. Message — сообщение; Task — работа с ID и состоянием; Artifact — её результат, например CSV. Это определения [A2A 1.0.0](https://a2a-protocol.org/v1.0.0/specification/). В отличие от интерфейса инструментов MCP, A2A описывает общение с самостоятельным агентным исполнителем. За серверным endpoint при этом могут работать MCP tools; см. [официальное сравнение](https://a2a-protocol.org/latest/topics/a2a-and-mcp/).

Учебный фрагмент Agent Card на S51 конкретизирует переход от описания к вызову. По навыку клиент оценивает пригодность исполнителя, а из `supportedInterfaces` выбирает совместимый binding и адрес. Ниже показан именно фрагмент: остальные обязательные поля полной карточки опущены. Поля сверены с [AgentCard, AgentSkill и AgentInterface, §§4.4.1, 4.4.5–6](https://a2a-protocol.org/v1.0.0/specification/#446-agentinterface).

```json
{
  "name": "Analytics",
  "skills": [{
    "id": "compare-releases",
    "name": "Сравнение релизов",
    "description": "Сравнивает ошибки до и после релиза",
    "tags": ["releases", "errors"]
  }],
  "supportedInterfaces": [{
    "url": "https://analytics.example/a2a",
    "protocolBinding": "JSONRPC",
    "protocolVersion": "1.0"
  }]
}
```

Сокращённый пример объектов A2A 1.0.0 с учебными значениями:

```json
{
  "jsonrpc": "2.0",
  "id": "req-7",
  "method": "SendMessage",
  "params": {
    "message": {
      "messageId": "m-7",
      "role": "ROLE_USER",
      "parts": [{"text": "Сравни ошибки r41/r42 за 30 минут; верни CSV"}]
    }
  }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": "req-7",
  "result": {
    "task": {
      "id": "t-17",
      "contextId": "c-4",
      "status": {"state": "TASK_STATE_COMPLETED"},
      "artifacts": [{
        "artifactId": "a-1",
        "name": "errors.csv",
        "parts": [{"text": "release,error_rate\nr41,0.01\nr42,0.04"}]
      }]
    }
  }
}
```

Сервер может также сразу вернуть `Message`, не создавая `Task`. ID запроса JSON-RPC связывает запрос с ответом; ID задачи обозначает саму работу. Формат результата не доказывает правильность анализа — это проверяется отдельно. Пример следует `SendMessage`/`SendMessageResponse` и базовому сценарию [спецификации](https://a2a-protocol.org/v1.0.0/specification/#941-sendmessage).

Binding определяет, как операции A2A отображаются в сетевые вызовы. По срезу 8 ноября 2026:

| Уровень | Подтверждённая поддержка | Практический смысл |
|---|---|---|
| Стандарт A2A 1.0.0 | JSON-RPC 2.0 по HTTP(S); HTTP+JSON/REST; gRPC по HTTP/2 с TLS | JSON-RPC задаёт вызовы методов, REST — HTTP-операции с ресурсными URL, gRPC — типизированные вызовы с Protobuf |
| Поток обновлений | SSE у JSON bindings; server stream у gRPC | SSE передаёт события по открытому HTTP-соединению |
| Официальный Python SDK v1.3.0 | Все три binding на client/server; gRPC требует extra | Не каждый конкретный сервер обязан включать все интерфейсы; совместимый выбирается по Agent Card |
| Push notifications | HTTP POST на настроенный webhook URL | Опциональная доставка обновлений задачи; принимающий endpoint настраивается отдельно |
| WebSocket и Kafka | Не входят в проверенные встроенные регистрации Python SDK | Нужен отдельный custom binding/adapter; его поддержку нельзя выводить из расширяемости SDK |

Основания: [нормативные bindings, §§9–11](https://a2a-protocol.org/v1.0.0/specification/), [ClientFactory Python SDK v1.3.0](https://github.com/a2aproject/a2a-python/blob/v1.3.0/src/a2a/client/client_factory.py), [webhook/push notifications](https://a2a-protocol.org/latest/topics/streaming-and-async/). Термин extension не равнозначен новому транспорту: [custom bindings](https://a2a-protocol.org/latest/topics/custom-protocol-bindings/) меняют сетевое отображение, extensions добавляют поведение поверх binding. Сторонние adapters и другие языковые SDK проверяются отдельно; этот вывод на них не распространяется.

## Глава III. Корпоративная среда агента

### III.1. Контракт и общий каталог

#### Назначение, вход и результат

Описание инструмента помогает выбрать операцию: зачем она нужна, какую запись меняет, что означают параметры и где заканчивается действие. JSON Schema описывает структуру данных: типы, обязательные поля и допустимые значения. Эти части контракта дополняют проверки прикладного сервиса.

Рассмотрим `set_incident_status`. Инцидент — запись о нарушении работы сервиса; `INC-42` — её идентификатор. Значение `investigating` означает, что расследование идёт, а `resolved` — что работа восстановлена. **Docstring** — документационная строка функции, которую адаптер может использовать как описание инструмента. Следующий пример описывает контракт, но не реализует бизнес-логику:

```python
def set_incident_status(
    incident_id: str,
    status: Literal["investigating", "resolved"]
) -> IncidentState:
    """Изменить состояние существующего инцидента.
    incident_id: ID записи, например INC-42.
    status: investigating — расследование идёт;
            resolved — работа восстановлена.
    Возвращает ID, состояние и ссылку source.
    Не создаёт инцидент и не уведомляет клиента."""
```

`IncidentState` обозначает результат с идентификатором инцидента, текущим статусом и ссылкой `source` на запись. Входная схема той же операции:

```json
{"type":"object",
 "properties":{
  "incident_id":{"type":"string"},
  "status":{"type":"string",
   "enum":["investigating","resolved"]}
 },
 "required":["incident_id","status"],
 "additionalProperties":false}
```

`type` задаёт тип, `required` перечисляет обязательные поля, `enum` ограничивает словарь, а `additionalProperties: false` запрещает лишние поля. `inputSchema` относится к `arguments`. Если задана `outputSchema`, она описывает `structuredContent`. Пример успешного результата:

```json
{"incident_id":"INC-42",
 "status":"resolved",
 "source":
  "https://issues.example/INC-42"}
```

Корректная строка идентификатора сама по себе не доказывает существование записи или допустимость перехода состояния. Название, описание и схема также не осуществляют проверку прав. [Anthropic: Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents), [MCP: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [MCP 2026-07-28: Schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts).

#### Ошибка протокола и отказ операции

Неизвестный метод или инструмент означает ошибку протокольного вызова. Если известный инструмент выполнился и сообщил прикладной отказ, результат может содержать `isError: true` и сведения, полезные для следующего шага. В примере недопустимого перехода достаточно сообщить состояние записи; внутренние секреты и диагностические детали сервера модели не нужны. Исправление имени операции и повтор запрещённого изменения — разные продолжения. `annotations` служат подсказками и не реализуют свойства безопасности. [MCP: Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

#### Каталог, registry и gateway

Каталог отвечает, где найти возможность, кто поддерживает её контракт и включена ли интеграция. Запись в каталоге сама по себе не предоставляет доступ к объекту. При большом числе команд определения и обслуживание вызовов могут находиться в разных компонентах.

В опубликованной 1 октября 2026 года архитектуре Uber MCP Registry образует control plane: хранит определения, владельцев и состояние включения. Proxy Gateway образует data plane: обслуживает поток вызовов и преобразует MCP во взаимодействия с native MCP servers либо существующими HTTP, gRPC и TChannel API. Это конкретная архитектура организации, а не обязательная топология протокола. [Uber: MCP Gateway, 2026](https://www.uber.com/us/en/blog/designing-mcp-gateway/).

### III.2. Полномочия

#### Участники и субъект доступа

**Identity** — удостоверенная системой идентичность пользователя или приложения. **Principal** — субъект, представленный системе для проверки прав. В защищённом HTTP MCP участвуют пользователь, Agent Host с MCP client, MCP resource server, Authorization Server и downstream API. Пользователь задаёт намерение, host ведёт агентный цикл, resource server предоставляет защищённые инструменты, Authorization Server выдаёт токены, а downstream API реализует прикладные операции, например в трекере задач. Имя сотрудника в аргументах модели не удостоверяет его identity. [MCP: Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [Microsoft Graph: Auth concepts](https://learn.microsoft.com/en-us/graph/auth/auth-concepts).

#### Как клиент получает токен

**Access token** подтверждает выданный доступ. **Audience** обозначает сервис, для которого токен предназначен, а **scope** — именованную область разрешённых операций. В рассматриваемом HTTP-взаимодействии MCP server сообщает расположение Protected Resource Metadata в `WWW-Authenticate`. Client получает `authorization_servers` и metadata выбранного Authorization Server. Этот discovery относится к получению доступа, тогда как `server/discover` главы I сообщает возможности MCP.

После регистрации клиента OAuth-поток включает вход пользователя, согласие при необходимости и обмен authorization code с PKCE. Параметр `resource` обозначает MCP server в запросах authorization и token. Затем клиент предъявляет токен в `Authorization: Bearer`, вне аргументов инструмента. Согласие OAuth разрешает доступ приложению; согласование конкретного изменения задачи остаётся отдельным решением host. [MCP: Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

#### Получатели и объектные права

Токен A предназначен MCP resource server. Сервер проверяет его действительность, issuer, срок, audience и scopes, затем право субъекта на конкретный объект, например `INC-42`. Для downstream API нужны отдельные полномочия B: токен MCP server нельзя просто переслать другому сервису как его собственный токен.

При **delegated access** доступ связан с пользователем. При **app-only** сервер использует собственную учётную запись приложения. MCP не задаёт единый on-behalf-of или token-exchange flow для всех downstream API. Общие credentials сервиса нельзя описывать как делегированные права сотрудника. Объектную авторизацию реализует прикладная система. В автономном примере этой лекции условие `owner == principal` иллюстрирует такую проверку в упрощённой форме. [MCP: Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [Microsoft Graph: Auth concepts](https://learn.microsoft.com/en-us/graph/auth/auth-concepts).

Согласование действия, авторизация сервиса и sandbox отвечают на разные вопросы. Одобрил ли сотрудник операцию? Разрешено ли субъекту менять эту запись? Какие файлы и сетевые ресурсы доступны процессу? Одобрение пользователя не выдаёт отсутствующих серверных прав, а файловая изоляция процесса не ограничивает автоматически полномочия внешнего API.

### III.3. Дополнительные возможности MCP

#### Resources и prompts

Кроме уже рассмотренных tools MCP предоставляет данные и шаблоны сообщений. **Resource** — адресуемое по URI содержимое, например runbook. Вызов `resources/read` возвращает `contents` с `uri`, `mimeType` и `text` либо `blob`. Приложение выбирает, какие данные добавить в контекст.

**Prompt** — именованный шаблон сообщений с параметрами. Например, `prompts/get` получает `incident_review` и аргумент `incident_id`, а возвращает `messages` с ролями и содержимым. Пользователь обычно выбирает такой сценарий подготовки сообщений. Чтение данных и получение шаблона не являются самостоятельным выполнением бизнес-операции. [MCP: Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), [MCP: Prompts](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts).

#### Elicitation: уточнение внутри операции

Elicitation запрашивает недостающие сведения через host и входит в Core MCP 2026-07-28. На схеме повторно использован основной шестисостоянийный цикл из лекции 3, карточка «Условия переходов», исходная S31: ветвь ожидания теперь возникает во время выполнения инструмента. Например, серверу нужен проект для подготовленной задачи. Host показывает форму сотруднику и после ввода продолжает взаимодействие. Это запрос сведений, который сохраняет отдельную авторизацию выбранного проекта.

**MRTR (Multi Round-Trip Requests)** связывает несколько обменов для одной операции. Первое сообщение содержит `tools/call` и поддержку формы в capabilities. Фрагмент HTTP-заголовков и полное тело сообщения приведены на технической карточке. Ниже именно JSON-RPC тело, без HTTP framing:

```json
{"jsonrpc":"2.0","id":71,"method":"tools/call","params":{
 "name":"prepare_issue","arguments":{"incident_id":"INC-42"},
 "_meta":{
  "io.modelcontextprotocol/protocolVersion":"2026-07-28",
  "io.modelcontextprotocol/clientInfo":{"name":"helpdesk","version":"1"},
  "io.modelcontextprotocol/clientCapabilities":{"elicitation":{"form":{}}}
 }}}
```

В ответе на исходный POST сервер возвращает `InputRequiredResult`, `inputRequests` и непрозрачное `requestState`. Отдельный входящий HTTP callback от сервера к клиенту в этой последовательности не используется:

```json
{"jsonrpc":"2.0","id":71,"result":{
 "resultType":"input_required","requestState":"opaque-state-1",
 "inputRequests":{"project":{"method":"elicitation/create","params":{
  "mode":"form","message":"Выберите проект для задачи",
  "requestedSchema":{"type":"object","properties":{
   "project":{"type":"string","enum":["SUPPORT","PLATFORM"]}
  },"required":["project"]}
 }}}}}
```

После выбора сотрудника клиент отправляет новый POST с новым JSON-RPC id. Аргументы операции сохраняются; `inputResponses` и `requestState` расположены непосредственно в `params`. Поля `continuation` в этой wire-схеме нет:

```json
{"jsonrpc":"2.0","id":72,"method":"tools/call","params":{
 "name":"prepare_issue","arguments":{"incident_id":"INC-42"},
 "inputResponses":{"project":{
  "action":"accept","content":{"project":"SUPPORT"}}},
 "requestState":"opaque-state-1","_meta":{
  "io.modelcontextprotocol/protocolVersion":"2026-07-28",
  "io.modelcontextprotocol/clientInfo":{"name":"helpdesk","version":"1"},
  "io.modelcontextprotocol/clientCapabilities":{"elicitation":{"form":{}}}
 }}}
```

Ключ `project` связывает ответ с запросом ввода. `accept` означает предоставленный ввод; также возможны `decline` и `cancel`. Client не интерпретирует `requestState`. Сервер проверяет его целостность, если состояние влияет на бизнес-логику или доступ. Конечный результат возвращается на новый id, с `resultType: complete` и данными подготовленной операции.

Form mode не предназначен для паролей, API keys или access tokens. URL mode проводит чувствительное взаимодействие вне канала формы; host показывает домен и запрашивает согласие. Получение значения проекта не предоставляет права на него. [MCP: Elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation), [MCP 2026-07-28: MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr), [MCP 2026-07-28: Schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts).

#### Tasks: длительная работа

Tasks имеет статус Beta extension на 8 ноября 2026 года. Поддержка расширения `io.modelcontextprotocol/tasks` объявляется в per-request capabilities и возможностях сервера. В редакции payloads 2026-07-28 сервер решает вернуть `CreateTaskResult` с `resultType: task`, `taskId` и полями задачи непосредственно в результате. Внешней оболочки `task` и флага `task` в исходном `tools/call` этот пример не использует.

`tasks/get` получает состояние, а при `completed` — вложенный `result` исходной операции. Отдельного `tasks/result` в этой редакции нет. Если требуется ввод во время исполнения, сервер сообщает `inputRequests`, а клиент передаёт `inputResponses` через `tasks/update`. Для HTTP-вызовов `tasks/get`, `tasks/update` и `tasks/cancel` заголовок `Mcp-Name` содержит taskId. Отмена кооперативна: запрос отмены не равен подтверждению остановки. Доступ к дескриптору задачи проверяет сервер. [MCP Tasks: Beta](https://modelcontextprotocol.io/extensions/tasks/overview), [MCP Tasks: 2026-07-28](https://github.com/modelcontextprotocol/ext-tasks/blob/cc9aaac1047a9440b07486e38f37060bbebeef4c/specification/2026-07-28/tasks.md).

#### MCP Apps: результат и интерфейс

Статус Apps в актуальном каталоге расширений — Stable. Технические примеры используют опубликованную редакцию Apps 2026-01-26, закреплённую SHA источника; её payloads не следует автоматически переписывать по правилам более позднего Core.

Tool metadata содержит вложенный `_meta.ui.resourceUri`, который указывает на `ui://` HTML-ресурс. Host получает его через `resources/read` с MIME `text/html;profile=mcp-app`, создаёт sandboxed iframe и передаёт результат через мост. Предварительная загрузка UI также допустима. Модель получает предназначенное ей описание и текст `content`; HTML и служебные UI metadata обслуживает host.

После `ui/initialize` и `ui/notifications/initialized` приложение общается с host через JSON-RPC поверх `postMessage`. Host отправляет `ui/notifications/tool-input` перед `ui/notifications/tool-result`. Запрос `tools/call` из iframe сначала поступает в host:

```json
{"jsonrpc":"2.0","id":8,"method":"tools/call",
 "params":{"name":"query_metrics","arguments":{"incident_id":"INC-42"}}}
```

Ответ host возвращается с тем же id. Учебные числа в `_meta.series` иллюстрируют данные для UI и не являются измерениями реального инцидента:

```json
{"jsonrpc":"2.0","id":8,"result":{
 "content":[{"type":"text","text":"Ошибки после релиза выросли"}],
 "_meta":{"series":[2,7,11]}}}
```

Host проверяет источник сообщения, поддержанные возможности и `_meta.ui.visibility`. Значение `visibility: ["app"]` скрывает инструмент из списка модели; без `app` в visibility вызов из приложения запрещён. Resource metadata `csp` и `permissions` описывают внешние origins и запрошенные возможности браузера; их применение контролирует host. Backend продолжает проверять доступ к данным. UI не получает новых полномочий только из-за интерактивного представления. Result `_meta` передаёт служебные данные приложению, а не текст модели. [MCP Apps: Stable](https://modelcontextprotocol.io/extensions/apps/overview), [MCP Apps: payloads 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/19256f52cad5517ba8272581ed2e11d6a81273d5/specification/2026-01-26/apps.mdx).

## Заключение

Рабочая среда сотрудника соединяет понятные операции, способы исполнения и отдельные границы доступа. Адаптер формирует удобный предметный контракт, host управляет агентным взаимодействием, а сервис проверяет операции над своими данными. MCP подключает возможности сервисов; A2A связывает самостоятельных агентных исполнителей. Resources и prompts дают контекст, Elicitation добавляет сведения, Tasks поддерживает длительную работу, Apps предоставляет интерактивное представление. Результат сквозного сценария — подготовленная задача и черновик ответа с проверяемыми источниками; публикация требует предусмотренного доступа и согласования.
