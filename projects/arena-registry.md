# Реестр тем для задания B

В каждой теме есть:
- объективная метрика;
- открытые или собираемые данные;
- простой baseline;
- большое пространство решений;
- почти везде — место для ML, а не только для ручных эвристик.

Часть тем взята из реестра научных задач лаборатории (метка «Н…» / «N-…»), часть — из рабочих задач лаборатории.

Одну тему могут взять несколько студентов. Тогда у каждого своя формулировка кейса и свои данные: например, разные классы плат, разные базы данных, разные GUI-приложения. Можно предложить **свою тему** (см. в конце). Тема выбирается через [форму выбора проекта](https://forms.yandex.ru/cloud/6adfe2ae4a052d8d4d96b3de).

В темах без LLM при оценке замер кандидата почти бесплатный, кампания может быть длинной. В темах с LLM каждый замер тратит токены, поэтому лимит решений и размеры split нужно считать заранее.

Во всех темах train, public и private берутся **из одного распределения** и делятся по семействам похожих экземпляров.

**Синтетические данные.** Если все разделы сделаны одним генератором, эволюция может выучить особенности генератора, а не задачу, и private этого не покажет. Поэтому:
- генератор должен быть разнообразным: несколько шаблонов, генерация через LLM в разных стилях, шум;
- метрику дополнительно проверяют на небольшой выборке, размеченной вручную или взятой из реальных открытых данных. Эта выборка не участвует в поиске.

## Карточки

### AR-01. Разводка печатных плат
- **Задача.** Дана плата из открытого проекта: контур, размещённые компоненты, список цепей. Существующие трассы удаляются. Нужно развести все цепи так, чтобы не было нарушений правил проектирования.
- **Данные.** **Выдаёт курс**: набор плат из открытых проектов с разбиением на train / public / private по семействам (один проект, одна серия, похожие ревизии), из одного пула.
- **Что эволюционирует.** Алгоритм трассировки:
  - порядок цепей;
  - стоимостная функция (Lee / A*);
  - rip-up and reroute;
  - работа со слоями и переходами.
- **Где ML.**
  - прогноз перегрузки участков платы (CNN/GNN по разметке платы);
  - выученный порядок цепей;
  - RL для трассировки отдельной цепи.
- **Метрика.** Программная, через DRC (например, `kicad-cli pcb drc`):
  - нарушение DRC обнуляет результат;
  - дальше — доля разведённых цепей, суммарная длина, число переходов.
- **Baseline.** **Выдаёт курс**: базовый трассировщик, с которого начинается эволюция.
- **Ориентир сверху.** Автотрассировщик Freerouting.
- **Почему интересно.** Эволюцию видно буквально, разводку можно нарисовать. Сравнение с промышленным автотрассировщиком сразу показывает, чего достигла арена.
- **Старт.** Датасет и baseline готовы, поэтому до эволюции можно дойти быстро. Основное время уходит на саму кампанию и разбор. Допускается упрощение задачи: 2 слоя, сеточная модель платы, классы плат от простых к сложным.

### AR-02. Протокол монтирования workdir при разных задержках сети
Тема напрямую улучшает задание A: агентский эволюционный подход к написанию системного софта.

- **Задача.** Локальная папка клиента монтируется в удалённый сандбокс. Нужно, чтобы типовые операции агента с ФС работали быстро при разных сетевых условиях и не ломалась консистентность.
- **Что эволюционирует.** Код протокола монтирования:
  - кэш атрибутов и содержимого с инвалидацией;
  - предвыборка дерева и метаданных;
  - ленивая подгрузка чанками;
  - батчинг, сжатие;
  - стратегия записи.
- **Где ML** (опционально). Прогноз следующих обращений агента к ФС для предвыборки.
- **Baseline.** SSHFS без кэша (`cache=no`) через обратный SSH-туннель или простой протокол «один запрос на операцию».
- **Метрика.** Взвешенное время набора сценариев ФС под профилями сети.
  - Сценарии: обход дерева и `stat`, `grep` по дереву, чтение многих мелких файлов, чтение крупного файла, серия записей.
  - Профили: RTT 1 / 20 / 80 / 200 мс, потери 0 / 1 %, через `tc netem`.
  - **Гейты корректности** (нарушение — кандидат невалиден):
    - запись агента видна у клиента за ≤ T;
    - правка клиента видна агенту за ≤ T;
    - нет потерянных записей;
    - соблюдается read-only;
    - нет выхода за пределы папки.
- **Данные.** Экземпляр = дерево файлов × сценарий × профиль сети. Деревья генерируются по распределениям числа и размеров файлов и глубины, снятым с реальных открытых репозиториев. Private — новые деревья из того же распределения.

### AR-03. Распознавание сканов таблиц
- **Задача.** Скан страницы с таблицей → структурированная таблица (HTML или JSON):
  - строки и столбцы;
  - объединённые ячейки;
  - многоуровневые заголовки;
  - текст каждой ячейки.
- **Что эволюционирует.** Пайплайн:
  - предобработка скана: выравнивание, бинаризация, шумоподавление;
  - детекция таблицы;
  - восстановление структуры: линии, ячейки, объединения, таблицы без рамок;
  - распознавание текста ячеек;
  - постобработка: числа, переносы, пустые ячейки.
- **Где ML.**
  - детекция линий и ячеек;
  - модели распознавания структуры таблиц (класса Table Transformer) на CPU;
  - классификатор «таблица с рамками / без рамок» для выбора ветки пайплайна.
- **Метрика.**
  - TEDS — сходство деревьев таблиц, учитывает и структуру, и текст;
  - TEDS только по структуре;
  - F1 по ячейкам (позиция + содержимое);
  - отдельно — точность числовых ячеек.
- **Данные.** Открытые датасеты таблиц с разметкой структуры: PubTabNet, FinTabNet, PubTables-1M, ICDAR cTDaR (там есть исторические сканы). Сверху накладываются синтетические искажения сканирования: шум, наклон, сжатие, низкое разрешение. Профиль искажений одинаков для всех разделов, деление — по исходным документам.
- **Baseline.** Поиск линий морфологией OpenCV → сетка ячеек → Tesseract в каждую ячейку.
- **Ограничение.** Только CPU. Тяжёлые GPU-модели (VLM-OCR) в тему не входят.
- **Почему интересно.** Таблицы без рамок и с объединёнными ячейками ломают простые подходы. Видно, на каких типах таблиц эволюция даёт прирост.

### AR-04. Подбор навыка по запросу (Н2-08)
- **Задача.** Дан запрос пользователя и каталог навыков. Нужно выбрать подходящий навык.
- **Что эволюционирует.** Ранжировщик и представление описаний навыков.
- **Где ML.**
  - эмбеддинги;
  - learning-to-rank;
  - кросс-энкодер или LLM-переранжирование.
- **Метрика.** accuracy@1, precision@3. Отдельно — устойчивость при росте каталога и на hard negatives.
- **Данные.** Каталог из 50–200 навыков (можно собрать из открытых каталогов навыков и MCP-серверов) и запросы к нему, включая перефразы и близкие по смыслу навыки.
- **Baseline.** BM25 по описаниям.
- **Оговорка.** Обязательны hard negatives: навыки, близкие по смыслу, и перефразы запросов. Без них метрика быстро упирается в потолок.

### AR-05. Маскирование ПДн на границе с моделью (Н2-01)
- **Задача.** Найти и обратимо заменить персональные данные в тексте перед отправкой модели.
- **Что эволюционирует.** Детектор и правила псевдонимизации.
- **Где ML.** NER-модели, классификаторы контекста, комбинация с правилами.
- **Метрика.**
  - recall и precision по классам ПДн, главное — recall при ограниченных ложных срабатываниях;
  - корректность обратной подстановки.
- **Данные.** Синтетические документы (договоры, письма, протоколы) с вшитыми ПДн известного класса и позиции.
- **Baseline.** Набор регулярных выражений.
- **Оговорка.** Данные синтетические, поэтому обязательно общее правило про синтетику: разнообразный генератор и проверка на небольшой вручную размеченной выборке открытых публичных текстов, где персональные данные уже есть (например, опубликованные документы организаций).

### AR-06. Оформление текстового документа по ГОСТ
- **Задача.** Взять текст без оформления (Markdown или «плоский» DOCX) и получить DOCX, оформленный по выбранному ГОСТу. Примеры стандартов:
  - ГОСТ 7.32 — отчёт о НИР;
  - ГОСТ Р 7.0.97 — организационно-распорядительные документы;
  - ГОСТ Р 7.0.100 — библиографические ссылки.
- **Данные.** Ищутся в интернете: открытые отчёты, ВКР и статьи из открытых репозиториев. Входы получаются удалением оформления из найденных документов. Лаборатория может немного помочь с примерами, но основную часть данных студент собирает сам.
- **Что эволюционирует.** Конвертер:
  - распознавание структуры (заголовки и их уровни, подписи, списки, таблицы, ссылки);
  - применение правил оформления.
- **Где ML.** Классификатор структурных элементов, обученный на открытых оформленных документах.
- **Метрика.** Программная:
  - число нарушений по чек-листу нормоконтроля: поля, шрифты, интервалы, нумерация, подписи, оформление списка литературы;
  - **гейт сохранности содержания**: текст без учёта оформления совпадает с исходным.
- **Важно.** Чекер нормоконтроля пишет студент. Он замораживается до поиска и покрывается тестами. Иначе эволюция начнёт подстраиваться под чекер, а не под ГОСТ.
- **Baseline.** Шаблон DOCX со стилями и правило «первая строка абзаца, набранная крупнее, — заголовок».
- **Оговорка.** До заморозки чекер проверяется на небольшой вручную размеченной выборке документов с известными нарушениями. Иначе эволюция подстраивается под понимание ГОСТа студентом, а не под сам ГОСТ.

### AR-07. Text-to-SQL, адаптивный к разным базам данных
- **Задача.** Навык, который отвечает на вопросы на естественном языке SQL-запросами и адаптируется к **незнакомой** базе данных: другая схема, другая предметная область, другой диалект.
- **Что эволюционирует.** Навык:
  - как он изучает схему (описание таблиц, примеры значений, связи);
  - связывание вопроса со схемой;
  - отбор примеров;
  - проверка и исправление запроса по ошибке выполнения;
  - адаптеры диалектов.
- **Где ML.** Эмбеддинги схемы и вопросов, отбор примеров, LLM.
- **Метрика.** Execution accuracy (результат запроса совпадает с эталонным) на базах, которых не было в train. Плюс токены и время.
- **Данные.** Открытые бенчмарки text-to-SQL с большим числом баз (Spider, BIRD). Базы можно развернуть в разных СУБД: SQLite, PostgreSQL, MySQL. **Семейство = база данных**: train, public и private содержат разные базы из одного пула.
- **Baseline.** Агент с Postgres MCP-сервером (например, Postgres MCP Pro) без специальной адаптации.
- **Оговорка.** Spider и BIRD почти наверняка встречались в обучении моделей, поэтому абсолютное качество может быть завышено. Сравнивать только с baseline на той же модели. Как вариант — добавить свои базы, которых нет в открытых бенчмарках.

### AR-08. Управление GUI-приложением кликами
- **Задача.** Студент выбирает GUI-приложение: калькулятор, графический редактор, Blender и т. п. Агент получает команду на естественном языке («создай сферу радиуса 2», «удали куб»). Навык превращает её в действия мыши и клавиатуры в интерфейсе.
- **Ограничение.** Действия выполняются **только кликами и клавиатурой**. Скриптовый API приложения и MCP для действий запрещены, ими пользуется только чекер.
- **Что эволюционирует.** Навык:
  - восприятие экрана: скриншот → элементы интерфейса;
  - библиотека элементарных действий и макросов;
  - планирование последовательности;
  - проверка результата по экрану.
- **Где ML.** Детекция элементов UI, OCR подписей, VLM-grounding «элемент → координаты».
- **Метрика.**
  - успешность по фактическому состоянию приложения: значение на дисплее калькулятора, сцена Blender, проверенная его API после сеанса;
  - число действий, время, токены.
- **Данные.** Генератор задач для выбранного приложения: шаблоны команд × параметры. Разделы — из одного генератора, по семействам операций.
- **Среда.** Приложение в контейнере с виртуальным дисплеем (Xvfb).
- **Baseline.** Захардкоженные координаты для фиксированного разрешения.
- **Оговорка.** Тяжёлая инфраструктура (виртуальный дисплей, скриншоты), нестабильные результаты, дорогой замер: много шагов, часто с VLM. Начинать с простого приложения уровня калькулятора, Blender — как расширение. Каждую задачу прогонять несколько раз.

### AR-09. Прогноз длины ответа LLM
- **Задача.** По тексту запроса (и, при необходимости, имени модели) быстро предсказать, сколько токенов модель сгенерирует на выходе и сколько придётся ждать, с интервалом неопределённости.
- **Что эволюционирует.** Предсказатель: признаки запроса, статистика по похожим запросам, модель, калибровка интервалов.
- **Где ML.** Регрессия по признакам, kNN по эмбеддингам похожих запросов, квантильная регрессия.
- **Метрика.**
  - MAE по log(токенов);
  - покрытие и ширина интервала (pinball loss);
  - ограничение на время предсказания.
- **Данные.** Открытые наборы запросов. Ответы на них один раз собираются от выбранной модели и фиксируются. Пул запросов делится по семействам (почти дубликаты в одном разделе).
- **Baseline.** Медиана длины ответа по всему train.
- **Почему интересно.** Прямо применимо к планированию нагрузки на модели. Оценка бесплатная: после сбора данных LLM не нужна.
- **Оговорка.** Длина ответа случайна даже на одном и том же запросе. Нужно собирать несколько ответов на запрос: разброс между ними — нижняя граница ошибки любого предсказателя, её указывают в отчёте.

### AR-10. Дизайн API инструментов для агента
- **Задача.** Есть готовая экосистема, в которой работает агент: сандбокс, сервис, система управления (например, своя среда из задания A, Git-сервер, трекер задач). Для неё нужно спроектировать инструменты (API), чтобы агент решал задачи управления с **минимумом токенов и ошибок**.
- **Что эволюционирует.** Интерфейс тулов:
  - гранулярность (один тул или несколько);
  - имена, схемы параметров, описания;
  - формат и объём ответов, пагинация;
  - тексты ошибок.
- **Что зафиксировано.** Харнес, модель, сама система, набор задач.
- **Метрика.**
  - доля решённых задач — гейт (не ниже порога);
  - среди прошедших — токены на задачу и число ошибочных вызовов тулов;
  - время.
- **Данные.** Задачи управления системой с чекерами итогового состояния. Задачи генерируются по шаблонам, разделы — из одного генератора по семействам задач.
- **Baseline.** Один тул «выполнить shell-команду» или прямой проброс существующего REST API.
- **Почему интересно.** На кривой эволюции видно, какие решения в дизайне API реально экономят токены. Результат переносится на задание A.
- **Оговорка.** Метрика шумная: разброс LLM между прогонами может быть больше разницы между кандидатами, а каждый замер — полный прогон агента. До поиска нужно оценить шум (несколько прогонов baseline) и по нему выбрать число повторов. Набор задач лучше небольшой, но с надёжными чекерами.

### AR-11. Маршрутизация запросов: выбор модели и режима харнеса
- **Задача.** Для каждого запроса выбрать конфигурацию, которой он будет обработан. Цель — минимизировать вычислительные затраты и время обработки всего потока запросов при сохранении нужного качества. Варианты конфигурации:
  - модель;
  - режим харнеса: глубина рассуждения, с тулами или без, один вызов или агентный цикл, бюджет контекста.
- **Что эволюционирует.** Роутер:
  - признаки запроса;
  - правила и пороги;
  - каскады «сначала дешёвая конфигурация, проверка, при необходимости эскалация».
- **Где ML.**
  - классификатор вероятности успеха каждой конфигурации;
  - прогноз токенов и времени (можно переиспользовать AR-09);
  - kNN по эмбеддингам похожих запросов.
- **Данные.**
  - Пул запросов с автоматически проверяемым ответом: открытые наборы по математике, коду, SQL, извлечению, задачи БАФ.
  - Каждый запрос **один раз** прогоняется через все конфигурации. Записываются качество, токены и время, и получается офлайн-матрица «запрос × конфигурация».
  - После этого кандидаты-роутеры оцениваются по матрице почти бесплатно. Каскады тоже считаются по ней, так как известны исходы всех ступеней.
  - Деление по семействам задач, разделы из одного пула.
- **Метрика.**
  - Гейт: качество не ниже порога, например ≥ 95 % от лучшей одиночной конфигурации.
  - Среди прошедших — суммарная стоимость и время (или площадь под кривой «стоимость — качество»).
- **Baseline.** Всегда самая сильная конфигурация. Для сравнения — всегда самая дешёвая и оракул (лучший выбор по матрице) как верхняя граница.
- **Стоимость.** Основные токены уходят на однократный сбор матрицы. Его нужно запланировать заранее.

### AR-12. Быстрый гардрейл для потока сообщений
- **Задача.** На вход идёт поток сообщений в LLM. Каждое нужно очень быстро отнести к одному из классов:
  - пропустить;
  - отбросить (дропнуть): инъекция, jailbreak, запрещённый контент, явный нецелевой спам.

  Обычные LLM в самом фильтре использовать **нельзя**: слишком медленно и дорого.
- **Подход.** Дистилляция:
  1. LLM-учитель размечает данные;
  2. на этой разметке обучается что-то быстрое и простое: TF-IDF + линейная модель, fastText, градиентный бустинг, маленький трансформер в ONNX int8.
- **Что эволюционирует.**
  - признаки и модель-ученик;
  - пороги;
  - каскад из быстрых фильтров;
  - стратегия разметки train: промпт учителя, число голосов, активный отбор примеров для разметки. Токены на разметку учитываются.
- **Что зафиксировано.**
  - эталонная разметка public и private: голоса нескольких LLM плюс ручная проверка выборки, заморожена до поиска;
  - железо для замера скорости.
- **Метрика.**
  - **Гейты:**
    - p99 задержки на одно сообщение ≤ 🔸 5 мс на CPU;
    - пропускная способность ≥ 🔸 N сообщений/с;
    - размер модели ≤ 🔸 M МБ;
    - LLM в рантайме нет.
  - **Основная:** TPR на опасных сообщениях при FPR ≤ 🔸 1 % на обычных.
- **Данные.**
  - открытые наборы jailbreak- и инъекционных промптов;
  - открытые наборы обычных пользовательских запросов;
  - всё это размечается LLM-учителем.

  Деление по семействам: перефразы одной атаки и один шаблон попадают в один раздел. Разделы берутся из одного пула.
- **Baseline.** Список стоп-слов и регулярных выражений. Второй baseline — TF-IDF + логистическая регрессия на сырой разметке учителя.
- **Ориентир сверху.** Качество самого LLM-учителя на private. Разница с ним — цена скорости.
- **Почему интересно.** Видно, как эволюция распределяет бюджет между качеством разметки, моделью-учеником и каскадом и где проходит граница «скорость — качество».
